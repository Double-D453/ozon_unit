# Дорожная карта: от Apps Script к SaaS

> Решение пользователя от **09.10.2026**: MVP переделать в SaaS.
> Горизонт — **«SaaS — цель, закладывать основу сейчас»**.
> Этот документ — ответ на вопрос «что именно закладывать сейчас».

---

## 1. Главный тезис: Apps Script в SaaS не мигрирует

Это не пессимизм, а технический факт, и его лучше принять сразу, чтобы не
проектировать не в ту сторону.

**Меняется не язык — язык остаётся JavaScript.** Меняются четыре фундаментальные
вещи, и каждая из них в Apps Script решена платформой, а в SaaS решается вами:

| | Apps Script | SaaS |
|---|---|---|
| Хранилище | Google Sheets (одна таблица = один магазин) | Postgres с `tenant_id` в каждой строке |
| Идентичность | аккаунт Google, один пользователь | регистрация, вход, роли, биллинг |
| Ключи Ozon | `Script Properties` — один набор на скрипт | зашифрованное хранилище **на каждого тенанта** + OAuth-поток подключения |
| Выполнение | триггер, **лимит 6 минут**, один поток | очередь задач, воркеры, ретраи, идемпотентность |

**Вывод:** переносится не код, а **знание**. Числа — в `docs/PORTABILITY.md`:
45% строк (весь API-клиент и парсеры) переезжают, 55% (таблица, меню,
оркестрация) пишутся заново — и должны писаться заново.

## 2. Что закладывать СЕЙЧАС (пока живём в Apps Script)

Пять вещей, каждая из которых дёшева сегодня и дорога потом.

### 2.1 Развязать логирование — **самое срочное**

Сейчас `sellerFetch_ → logMsg_ → sheet_ → SpreadsheetApp`. Из-за одной строчки
лога весь API-слой транзитивно зависит от Google Sheets.

**Действие:** `logMsg_` пишет в внедряемый sink, по умолчанию — на лист.
~10 строк кода. Результат: 50 функций становятся переносимыми без правок,
а мок в тестах перестаёт изображать таблицу ради лога.

### 2.2 Не расширять слой таблицы

Каждая новая фича, которая читает колонки по индексам, увеличивает долг.
Правило уже сформулировано и проверено на практике:
**новые поля добавлять в конец листа, не вставлять в середину.**
Так «Продажи» расширились с 9 до 13 колонок, не сломав `salesRevenueMap_`.

### 2.3 Держать доменное ядро отдельно и тестировать его отдельно

`core/` — уже сделано: юнит-экономика, комиссия, конструкторы запросов.
Около 900 строк JS, 79 проверок, ни одной зависимости от платформы.
**Любая новая бизнес-логика должна попадать туда, а не в `03_Sync.gs`.**

Это единственный способ не переписывать расчёты третий раз.

### 2.4 Валидатор схемы как часть CI

`tests/schema.js` сверяет тела запросов с официальной OpenAPI-схемой Ozon.
Он уже поймал ошибку, которая стоила прогона: на теле v0.6 находит 5 запрещённых
полей (`dir`, `offset`, `filter.status`, `with.barcodes`, `with.translit`) плюс
превышение лимита. Проверка закреплена постоянным тестом `tests/negative.js`.

**В SaaS это становится критичнее**, а не менее важно: методов будет больше,
а Ozon продолжит их отключать (за 2025–2026 отключено три, см. `docs/API-MAP.md` §12).

### 2.5 Проектную схему БД описать раньше кода

`docs/DATA-MODEL.md` §10 уже содержит маппинг листов на сущности.
Три вещи, которые **нельзя добавить потом**:
1. `tenant_id` в каждой таблице;
2. версионность снапшотов (тарифы меняются, нужен расчёт «как было в сентябре»);
3. идемпотентность синков (естественный ключ + отметка выполненной работы).

## 3. Целевая архитектура

```
┌─────────────────────────────────────────────────────────────────┐
│  Веб-интерфейс (Next.js / SvelteKit)                            │
│  подключение магазина · дашборд наценки · pricelist · экспорт   │
└───────────────────────────┬─────────────────────────────────────┘
                            │ REST/GraphQL, auth per tenant
┌───────────────────────────▼─────────────────────────────────────┐
│  API-сервер (Node/TS)                                           │
│  · tenants, users, billing                                      │
│  · vault: ключи Ozon зашифрованы на тенанта                     │
│  · читает из Postgres, НЕ ходит в Ozon синхронно                │
└───────────────────────────┬─────────────────────────────────────┘
                            │ задачи
┌───────────────────────────▼─────────────────────────────────────┐
│  Очередь (BullMQ / SQS) + воркеры                               │
│  · sync-prices · sync-sales · sync-ads · sync-commission        │
│  · ретраи, дедупликация, rate-limit по каждому ключу Ozon       │
│  ┌────────────────────────────────────────────────────────┐    │
│  │  ★ core/ — переезжает из Apps Script без правок ★      │    │
│  │  unit-economics · commission · ozon-endpoints          │    │
│  │  perf-csv-parser                                       │    │
│  └────────────────────────────────────────────────────────┘    │
└───────────────────────────┬─────────────────────────────────────┘
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
   Postgres            Ozon Seller API    Ozon Performance API
   (+ снапшоты)
```

### Ключевые отличия от Apps Script

**1. API-сервер никогда не ходит в Ozon синхронно.**
В Apps Script пользователь ждал 4,5 минуты, глядя в меню. В SaaS он нажимает
«Обновить» и получает задачу; данные появляются в интерфейсе по готовности.
Это же снимает ограничение на длительность: волны по 3×10 кампаний с
предохранителем по времени становятся не нужны — остаётся только уважать
лимиты самого Ozon.

**2. Rate-limit нужен на каждого тенанта.**
`/v1/analytics/data` без Premium — **1 запрос/мин, 50/сутки**. С десятками
магазинов это исчерпается мгновенно, если лимитировать глобально.
Нужен токеновый бакет **на ключ тенанта**, а не на воркер.

**3. Состояние кампании — в БД, а не в `Script Properties`.**
Сейчас обработанные кампании копятся в чанках по 600 id из-за лимита значения
9 КБ, ключи `DRR_DONE_0…`. В SaaS это таблица `campaign_sync_state` с
`tenant_id`, `campaign_id`, `period`, `status`, `updated_at`.
Побочно решается проблема «помечать обработанной только если отчёт реально
получен» — статус становится явным полем.

**4. Отчёт о реализации — самое узкое место по данным.**
`/v1/finance/realization/by-day` требует Premium Plus и не глубже 32 дней.
В SaaS у разных тенантов будут **разные подписки**. Значит:
- каскад источников (по дням → за месяц → отправления) становится обязательным,
  а не желательным;
- факт подписки надо определять через `/v1/roles` и хранить, а не спрашивать
  пользователя (сейчас это `HAS_PREMIUM_PLUS: true` в конфиге — так не масштабируется).

**5. История вместо перезаписи.**
«Факт Ozon» перезаписывается целиком — история тарифов теряется. В SaaS каждый
синк пишет снапшот с датой. Это даёт ретроспективный расчёт наценки и аудит
изменения цен — и то, и другое станет платной фичей.

## 5. Что может пойти не так

| Риск | Почему вероятен | Что делать |
|---|---|---|
| **Ozon отключит метод** | За 2025–2026 отключено три, включая основной финансовый | Валидатор схемы в CI + ежеквартальная сверка со свежей схемой |
| **У тенанта нет Premium Plus** | Отчёт о реализации — единственный точный источник фактической комиссии | Каскад источников + честно показывать точность, а не выдавать оценку за замер |
| **Себестоимость не задана** | В своём магазине таких 111 из 1265 | Правило B15 уже сформулировано: помечать, не считать. В SaaS это онбординг-проблема, её надо решать интерфейсом |
| **Ключи утекут** | Мультиарендность = чужие деньги и товары | Vault, шифрование, отсутствие ключей в логах, ротация. Правило C1 уже есть — распространить на SaaS |
| **Лимиты аналитики** | 50 запросов/сутки без Premium | Кэширование снапшотов, расписание вне пика, батчинг по SKU |
| **Данные 1С у каждого свои** | Себестоимость и кратность приходят не из Ozon | Импорт CSV/Excel как первый класс, а не «потом доделаем» |

## 6. Что делать с Apps Script

**Не бросать.** Он остаётся полезным до конца Фазы 1 по трём причинам:

1. Это **эталон для сверки**: цифры в таблице — то, с чем должен совпасть SaaS.
2. Это **прод работающий магазин**: расчёт наценки нужен сейчас, а не через квартал.
3. Это **стенд для проверки гипотез про API** — дешевле сломать таблицу, чем продакшн.

Замораживать имеет смысл на Фазе 2, когда SaaS начнёт давать те же числа.

**Единственное, что стоит менять в Apps Script дальше** — рефакторинг
логирования из п. 2.1 и закрытие этапов Э2–Э4. Новые фичи в таблицу добавлять
не стоит: они увеличивают объём переписывания.
