# Карта API Ozon — что работает, что отключено, где ловушки

> **Это самый дорогой документ в репозитории.** Каждая строка здесь оплачена
> прогоном на живом аккаунте или чтением официальной OpenAPI-схемы.
> В SaaS переезжает именно это знание, а не код Apps Script.
>
> Источник истины по формам запросов — **официальная схема**, а не статьи,
> не SDK на Go и не ответы в чатах. Зеркало схемы обновляется ежедневно:
> `raw.githubusercontent.com/vispar-tech/ozon-seller-api-schema/main/schemas/ozon-seller-api-openapi.json`
> Локальная копия (4,2 МБ, 482 пути, снята 08.10.2026): `schema/ozon-seller-api-openapi.json`.
> Выжимка тел 19 методов, которую читают тесты: `schema/ozon_paths.json`.

Состояние на **октябрь 2026**. Проверяйте даты — Ozon отключает методы без длительного
переходного периода, и отключённый метод выглядит в логе так же, как отсутствующее право.

## 0. Правила игры, которые экономят часы

1. **Лишнее поле в теле = HTTP 400.** Ozon не игнорирует неизвестные поля.
   Ошибка приходит как `code: 3, message: "В теле запроса есть лишние параметры: …"`.
   Именно так в v0.6 сломался расчёт комиссии: в `/v3/posting/fbo/list` ушли `dir`,
   `offset`, `filter.status`, `with.barcodes`, `with.translit` — их там нет.
   Ни один мок-тест это не поймал. Отсюда — валидатор `tests/schema.js`.
2. **403 «Недостаточно прав» неразличим с «данных нет»** в коротком логе.
   Поэтому есть `/v1/roles` — он отдаёт точный список методов, доступных ключу.
3. **Формы FBO и FBS — разные.** Это не опечатка в документации, а два разных
   поколения API. См. раздел 4.
4. **Ответ FBO приходит без обёртки `result`.** `response.postings`, а не
   `response.result.postings`. Чтение «правильного» пути молча даёт пустой массив.
5. **Дата `date_to` в будущем = 400** в `/v1/analytics/data`. Функция, которая
   возвращает «завтра» как конец периода, ломает всю аналитику.

## 1. Хосты

| Назначение | Хост | Комментарий |
|---|---|---|
| Seller API | `api-seller.ozon.ru` | Заголовки `Client-Id`, `Api-Key` |
| Performance API | `api-performance.ozon.ru` | **Не `performance.ozon.ru`** — тот мёртв |
| Кабинет Performance | `performance.ozon.ru` | Только для человека, не для API |

**`performance.ozon.ru` мёртв с 15.01.2025** — отвечает `307 Temporary Redirect`
на nginx-страницу. `UrlFetchApp` в Apps Script **не повторяет POST при 3xx**
(только GET/HEAD), поэтому запрос молча возвращает HTML. Лечится функцией
`fetchWithRedirects_` (`02_OzonPerformance.gs`), которая следует за `Location` вручную.

В SaaS эта проблема исчезает сама: `fetch` в Node следует за редиректами.

## 2. Аутентификация

### Seller API
```
Client-Id: <client id>
Api-Key:   <ключ>
Content-Type: application/json
```
Ключ создаётся в кабинете продавца. Права ключа — **`POST /v1/roles`** с пустым телом `{}`:
```json
{ "expires_at": "2026-12-31T21:00:00Z",
  "roles": [ { "name": "Админ", "methods": ["/v3/product/list", "/v1/analytics/data", "…"] } ] }
```
`methods` — точный список путей, разрешённых ключу. **Используйте его для диагностики
вместо проб и ошибок**: `diagRoles()` сверяет нужные методы со списком и печатает
`✓/✗` по каждому.

⚠ У ключа есть `expires_at`. Просроченный ключ даёт те же 403, что и отсутствующее право.

### Performance API
Токен получается отдельно и **живёт ~1800 секунд**:
```
POST /api/client/token
{ "Client-Id": "…", "Api-Key": "…" }
→ { "access_token": "…", "expires_in": 1800 }
```
Дальше — `Authorization: Bearer <access_token>`. Токен надо кэшировать и
перезапрашивать по истечении, а не на каждый отчёт.

**Ключи Seller и Performance — разные сущности.** Права выдаются в разных местах
кабинета. Это частая причина «одна интеграция работает, вторая нет».

## 3. Товары, цены, остатки

| Метод | Тело | Пагинация | Ответ |
|---|---|---|---|
| `POST /v3/product/list` | `{filter:{visibility}, limit≤1000, last_id}` | `last_id` | `result.items[{offer_id, product_id, archived}]`, `result.total` |
| `POST /v3/product/info/list` | `{offer_id[]}` или `{sku[]}` | — | `result.items[]` |
| `POST /v5/product/info/prices` | `{filter:{offer_id[],visibility}, limit≤1000, cursor?}` | `cursor` | `items[]`, `cursor`, `total` |
| `POST /v4/product/info/stocks` | `{filter:{offer_id[],visibility}, limit≤1000, cursor?}` | `cursor` | `result.items[]` |

### `/v5/product/info/prices` — главный источник тарифов

Проверенный образец: «Кромка-Дуб-44мм-5м.п.», `product_id` 476340284, `sku` 907795882.

```jsonc
{
  "acquiring": 10.73,                  // ⚠ В КОРНЕ ЭЛЕМЕНТА, не внутри price
  "offer_id": "Кромка-Дуб-44мм-5м.п.",
  "price": {
    "price": 1757.0,
    "old_price": 2355.0,
    "min_price": 1615.0,
    "marketing_seller_price": 1073.0,
    "marketing_price": 0,              // отключено 12.11.2025, всегда пусто
    "vat": "0.22"                      // ⚠ ДОЛЯ, а не проценты
  },
  "commissions": {
    "sales_percent_fbo": 49.5, "sales_percent_fbs": 49.5,
    "sales_percent_rfbs": 49.5, "sales_percent_fbp": 49.5,
    "fbo_fulfillment": …, "fbo_direct_flow_trans_min_amount": 75.0,
    "fbo_direct_flow_trans_max_amount": 254.0,
    "fbo_deliv_to_customer_amount": 25.0,
    "fbo_return_flow_amount": 115.0,
    "fbs_first_mile_min_amount": 0.0, "fbs_first_mile_max_amount": 10.0,
    "fbs_direct_flow_trans_min_amount": 75.0, "fbs_direct_flow_trans_max_amount": 254.0,
    "fbs_deliv_to_customer_amount": 25.0, "fbs_return_flow_amount": 254.0
  }
}
```

**Три ловушки, каждая стоила прогона:**
- `acquiring` лежит **в корне элемента**, а не внутри `price`. В v0.4 его искали
  внутри `price` → ни одного значения из API, везде оценка по умолчанию.
- `vat` приходит **долей** (`"0.22"`), а таблица ждёт проценты. Приводим через `ratioToPercent_`.
- `sales_percent_*` — это **списочная** ставка. Фактически удерживают меньше
  (скидка за отсрочку выплаты). Раздел 6.

**Витринная цена покупателя недоступна.** Поле `marketing_price` отключено
**12.11.2025** и приходит пустым. `marketing_seller_price` — это цена продавца
со скидкой Ozon, а не то, что видит покупатель. Получить фактическую витринную
цену через API нельзя; пользователь это пробовал и подтвердил.

## 4. Отправления: FBO и FBS — РАЗНЫЕ формы запросов

Это самое частое место ошибок. Таблица различий:

| | `/v3/posting/fbo/list` | `/v3/posting/fbs/list` |
|---|---|---|
| Направление | `sort_dir`: `ASC`/`DESC` | `dir`: `asc`/`desc` |
| Смещение | **`cursor`** (строка) | **`offset`** (число) |
| Лимит | **1..100** | до 1000 |
| `with` | `analytics_data`, `financial_data`, `legal_info` | + `barcodes`, `translit` |
| `translit` | отдельный флаг **верхнего уровня** | внутри `with` |
| Фильтр по статусу | `filter.statuses[]` (массив) | `filter.status` (строка) |
| Ответ | `{cursor, has_next, postings[]}` — **БЕЗ `result`** | `{result:{postings[], has_next, count_total}}` |

**Если послать FBO форму FBS → HTTP 400 «лишние параметры».**
**Если читать `result.postings` у FBO → молча пустой массив.** Обе ошибки дают
одинаковый симптом: «Комиссия факт пустой».

### Финансовые данные внутри отправления

`PostingFinancialDataProduct`:
```jsonc
{ "commission_amount": 869.68,   // ⚠ НЕОДНОЗНАЧНО: за единицу или за позицию
  "commission_percent": 49.5,
  "price": 1757.0, "payout": …, "quantity": 1, "product_id": 476340284 }
```

**`commission_amount` неоднозначен** — документация не говорит, за единицу товара
это сумма или за всю позицию. Гадать нельзя: при `quantity > 1` ошибка ровно вдвое.
Решение — **самокалибровка**: сравниваем `commission_amount / price` с
`commission_percent`; если расхождение ≈ `quantity`, делим на `quantity`.
Реализовано в `diagCommission`.

## 5. Аналитика продаж

### `POST /v1/analytics/data`

```jsonc
{ "date_from": "2026-09-28", "date_to": "2026-10-12",
  "metrics": ["revenue","ordered_units","delivered_units","returns","cancellations"],
  "dimension": ["sku"], "filters": [], "sort": [],
  "limit": 1000, "offset": 0 }
```

**Обязательны:** `date_from`, `date_to`, `dimension`, `metrics`, `limit`.

| Метрики | Кому доступны |
|---|---|
| `revenue`, `ordered_units` | **всем** |
| `delivered_units`, `returns`, `cancellations`, `hits_view`, `hits_tocart`, `conv_tocart`, `session_view`, `position_category` | **Premium Plus** |

| Измерения | Кому доступны |
|---|---|
| `sku`, `spu`, `day`, `week`, `month` | всем |
| `year`, `category1`, `category2`, `brand`, `modelID`, `descriptionType` | Premium Plus |

**Ограничения:**
- **Не более 14 метрик** за запрос. Превышение → `InvalidArgument`, а не усечение.
- **`date_to` не может быть в будущем** → HTTP 400.
- Без подписки Premium: **1 запрос/мин, 50 запросов/сутки**, глубина истории **3 месяца**.
- С Premium Plus лимиты заметно выше, а глубина больше.

### ❌ `adv_sum_all` НЕ СУЩЕСТВУЕТ

**Расходов на рекламу аналитика не отдаёт ни с какой подпиской.** В официальной
схеме Seller API — **0 вхождений** строки `adv_sum_all`. Это проверено grep-ом
по схеме от 08.10.2026, а не по статье.

Раньше этот факт был записан в коде как «метрика доступна с Premium, скрипт
пробует её и откатывается». Запрос был обречён с самого начала. **Расходы на
рекламу — только Performance API**, и это единственный путь к ДРР.

## 6. Комиссия: где взять ФАКТИЧЕСКУЮ ставку

### 6.1 Проблема

Списочная ставка (49,5%) приходит в `/v5/product/info/prices`. Но фактически
Ozon удерживает меньше — за счёт **скидки за отсрочку выплаты**. При отсрочке
**84 дня** скидка порядка **1,5 п.п.**, то есть факт ≈ 48,0–48,3%.

**Скидка нигде не отдаётся отдельным полем.** Её нет:
- в `/v5/product/info/prices` (ни в цене, ни в комиссиях);
- в тарифных справочниках;
- в `/v1/finance/accrual/*` (там сборы, а не ставка).

Она видна только в личном кабинете: **«Финансы → Начисления» / «Экономика магазина»**,
в УПД-1 и в отчёте о реализации.

**С 28.09.2026 скидка уменьшена в среднем на 1 п.п.** Значит, любые захардкоженные
числа устаревают — нужна кнопка перемера, а не константа.

**Тарифные сетки в публичных источниках расходятся**, доверять им нельзя:
- tochka: 14 дн → 0,45%, 84 дн → 2,7%, 168 дн → 5,4%
- litestat: 45 дн → 1,5%

Вывод: **мерить по своим данным**. Косвенное подтверждение величины: в исходном
файле V3 фактические ставки в колонках AP/AU стояли как **48,3%** при списочной
49,5% — разница 1,2 п.п., что согласуется с «около 1,5 п.п.» и с уменьшением
скидки 28.09.2026.

### 6.2 Рабочее решение: отчёт о реализации

**Требуется подписка Premium Plus (или Premium Pro).** У пользователя она активна.

| Метод | Тело | Глубина | Когда готов |
|---|---|---|---|
| `POST /v1/finance/realization/by-day` | `{day, month, year}` | **не глубже 32 дней** от сегодня | на следующий день |
| `POST /v2/finance/realization` | `{month, year}` | за календарный месяц | **не позднее 5-го числа** следующего месяца; периоды с августа 2023 |
| `POST /v1/finance/realization/posting` | `{month, year}` | позаказно | как месячный |

⚠ `/v2/finance/realization` **недоступен для ТОО «ОЗОН Маркетплейс Казахстан»**.

### Структура строки отчёта

```jsonc
{ "item": { "offer_id": "…", "sku": 910000, "name": "…", "barcode": "…" },
  "commission_ratio": 0.495,        // ⚠ ставка по категории; может прийти и 0.495, и 49.5
  "seller_price_per_instance": 1757.0,
  "delivery_commission": {
    "amount": 10000.0,              // «Реализовано на сумму»
    "standard_fee": 4800.0,         // «Базовое вознаграждение Ozon» = ЧТО УДЕРЖАЛИ
    "commission": 0,                // «Итого комиссия со скидками» — только до 30.04.2024
    "total": 5200.0,                // «Итого к начислению»
    "quantity": 10, "price_per_instance": …, "bonus": …,
    "bank_coinvestment": …, "stars": …, "pick_up_point_coinvestment": …,
    "compensation": …
  },
  "return_commission": { /* те же поля для возвратов */ }
}
```

### 6.3 Формула скидки

```
ставка списочная, %   = commission_ratio            (нормализовано: доля → %)
комиссия факт, %      = standard_fee / amount × 100
СКИДКА, п.п.          = ставка списочная − комиссия факт
```

**Три вещи, без которых результат неправдоподобен:**

1. **`ratioToPercent`** — нормализация `commission_ratio`. Ozon может отдать и
   `0.495`, и `49.5`. Без нормализации разница уезжает на порядок.
2. **Взвешивание по выручке**, а не среднее по артикулам. Артикул с оборотом 10 ₽
   не должен влиять так же, как артикул на 1 млн ₽.
3. **Самоконтроль:** `amount − standard_fee ≈ total`. Если не сходится — значит
   `standard_fee` не вся комиссия (есть бонусы, коинвестиции, компенсации), и
   скидке верить нельзя. Допуск 3%.

**Пороги доверия** (правила в `core/commission.js`, функция `isTrustworthy`):
артикулов ≥ 10, сумма реализации > 0, скидка в диапазоне 0,05…6 п.п.,
самоконтроль сошёлся. Иначе значение **не подставляется** — остаётся дефолт,
и это записывается в лог с обоснованием.

### 6.4 Каскад источников (что делает `diagCommission`)

1. **Отчёт о реализации по дням** — суммируем последние 14 дней (параметр
   `REALIZATION_DAYS`; максимум 31 из-за ограничения 32 дня).
2. Если пусто/недоступно → **месячный отчёт** за предыдущий месяц.
3. Если и он недоступен → **отправления FBO/FBS** (`commission_amount` с
   самокалибровкой). Менее точно: там нет `commission_ratio`, ставку берём из цен.
4. Если артикулов < 10 → параметр **не трогаем**, только логируем.

Результат пишется в «Параметры» **B14** с обоснованием в **C14**.

## 7. Финансы: отключённые методы и замена

### ❌ Отключено 08.09.2026
- `POST /v3/finance/transaction/list`
- `POST /v3/finance/transaction/totals`

**Это был основной источник операций по счёту.** Любой код, написанный до осени
2026 по статьям в интернете, обращается именно к нему и получает ошибку.

### Замена — начисления (accruals)

| Метод | Тело | Что отдаёт |
|---|---|---|
| `POST /v1/finance/accrual/postings` | `{posting_numbers[] ≤ 200}` | `posting_accruals[].accruals[]{accrual_date, accrued, quantity, seller_price, sku, type_id}` |
| `POST /v1/finance/accrual/by-day` | `{date, last_id?}` | `accruals[]{accrual_id, accrued_category: POSTING\|ITEM\|NON_ITEM, date, unit_number, total_amount, posting, item_fees, non_item_fee, container_fees}` + `last_id` |
| `POST /v1/finance/accrual/types` | `{}` | `accrual_types[]{id, name}` — справочник типов |

**Что важно понимать:**
- `accrual/*` несёт **СБОРЫ** (логистика, хранение, эквайринг, штрафы, услуги).
- **Выручка за продажу** там отдельно не отдаётся — она из отчёта о реализации.
- **Комиссия за продажу** сходится до рубля из `accrual/postings`.
- `accrual/by-day` **комиссии за продажу НЕ несёт**.
- `last_id` из `by-day` **живёт 15 минут** — нельзя сохранить и продолжить завтра.
- `accrual_id` = старый `operation_id` (переименование при миграции).
- `accrued_category` разделяет начисления за отправление, за товар и вне-товарные.

**Вывод для модели:** полная финансовая картина собирается из **двух** источников —
отчёт о реализации (выручка + комиссия + скидки) и accruals (сборы). Одного
недостаточно, и они не заменяют друг друга.

## 9. Performance API — единственный источник расходов на рекламу

### Последовательность вызовов

```
1. POST /api/client/token
      {Client-Id, Api-Key} → access_token (~1800 c)

2. GET  /api/client/campaign
      → list[]{id, title, state, advObjectType, fromDate, toDate, dailyBudget}

3. POST /api/client/statistics
      {dateFrom, dateTo, campaignIds[≤10], grouping[day|campaign|banner|…]}
      → {result: [uuid, …]}          // задание ставится в очередь

4. GET  /api/client/statistics/{uuid}
      → {result: {statisticsStatus: "DONE"|"IN_PROCESS"|…, statistics: [{…}]}}

5. GET  /api/client/statistics/report?UUID=<uuid>
      → 1 кампания:  CSV
        несколько:   ZIP-архив с CSV
```

### Ограничения

| Ограничение | Значение |
|---|---|
| Кампаний в одном запросе `statistics` | **не более 10** |
| Заданий в очереди одновременно | **не более 3** |
| Период отчёта | **не более 1 года** |
| Время жизни токена | ~1800 секунд |
| Лимит выполнения Apps Script | **6 минут** → предохранитель 4,5 мин |

### Формат CSV (проверен на живых отчётах)

- Разделитель — **точка с запятой `;`**, есть **BOM** (`\ufeff`).
- **Строка 1** — заголовок кампании (название, период), не данные.
- **Строка 2** — заголовки колонок, **17 штук**.
- **Строка 3** — строка «Всего» (итог), её надо пропускать.
- Дата — колонка **«День»**. Формат бывает и `2026-09-28`, и `28.09.2026`.
- Выручка — колонка **«Продажи в продвижении, ₽»**.
- Расход — «Списано за показы, ₽» / «Списано за клики, ₽».
- Числа могут приходить с пробелами-разделителями тысяч и запятой как десятичной.

**Имя файла внутри ZIP: `<campaignId>_<период>.csv`.** Отсюда `perfIdFromFileName_`
извлекает id регулярным выражением `/(\d{4,})/`.

### Ловушки парсинга, каждая стоила итерации

1. **Регулярка на «выручка» / «revenue» не находит ничего** — колонка называется
   «Продажи в продвижении, ₽». Парсер v0.3/v0.4 возвращал нули.
2. **Опечатка «ддр» вместо «дрр»** → `salesAll = 0` → ДРР ноль у всех.
   При отладке кириллицы сверяйте `codePointAt`, а не глазами.
3. **Определение типа ответа.** `HTTPResponse` в Apps Script **не имеет
   `getContentType()`**. Рабочий способ: `blob.getContentType()` внутри `try`
   плюс проверка первых байт на сигнатуру ZIP (`0x50 0x4B` = «PK»).
4. **Масштаб.** В кабинете пользователя **1663 кампании**. Стратегия:
   отбор по `state` (только активные/завершённые в периоде) → волны по 3×10
   кампаний → накопление обработанных id в `Script Properties` (`DRR_DONE_0…`)
   → предохранитель по времени 4,5 мин.
5. **Помечать кампанию обработанной только если отчёт реально получен.**
   Иначе при обрыве по времени она теряется навсегда.
6. **Script Properties: лимит значения 9 КБ** → чанки по 600 id.
   ⚠ **Никогда не вызывать `deleteAllProperties()`** — сотрёт API-ключи.

### ДРР — определение

**ДРР = расход на рекламу / ВСЯ выручка товара** (и органическая, и рекламная).
Это требование пользователя, а не «расход / продажи в продвижении».
Числитель — Performance API, знаменатель — `/v1/analytics/data` (`revenue` по `sku`).
Отсюда обязательны два синка и их согласование по периоду.

## 10. Возвраты

`POST /v1/returns/list` — `{filter:{…}, last_id, limit}` → `returns[]`.
Учёт возвратов и невыкупов — требование пользователя, фактическое значение
берётся **средним по SKU**.

С подпиской Premium Plus часть данных удобнее брать из аналитики:
`returns` и `cancellations` против `delivered_units` → **% выкупа**:
```
% выкупа = delivered_units / ordered_units
```
Защита обязательна: при `ordered_units = 0` или `delivered_units = 0` процент
**не пишется** (иначе 0% или Infinity в модели). Реализовано в `syncSales`.

## 11. Выгрузка цен (этап Э5 — ещё не включён)

`POST /v1/product/import/prices`
```jsonc
{ "prices": [ { "offer_id": "…", "price": "1757", "old_price": "2355",
                "min_price": "1615", "currency_code": "RUB", "vat": "0.22",
                "auto_action_enabled": "UNKNOWN|ENABLED|DISABLED" } ] }
```
Ответ — `task_id`, статус проверяется через `POST /v1/product/import/info` `{task_id}`.

**Контроль перед отправкой обязателен**, иначе Ozon уводит товар в карантин цен:
`price > 0`, `old_price ≥ price`, `min_price ≤ price`.

⚠ **Сейчас в Ozon ничего не отправляется.** `previewExport` — заглушка, которая
только показывает, что было бы отправлено. Включение записи — отдельное решение
пользователя на этапе Э5.

## 13. Как поддерживать эту карту живой

1. Раз в квартал скачать свежую схему с зеркала `vispar-tech/ozon-seller-api-schema`
   и прогнать `tests/schema.js` — он покажет, какие тела запросов перестали
   соответствовать.
2. Дифф по `ozon_paths.json` (19 методов, которыми мы пользуемся) — быстрый
   способ увидеть изменение формы.
3. Любой новый метод добавлять сначала в `schema/ozon_paths.json`, потом в
   `core/ozon-endpoints.js`, потом в код. Порядок обязателен: иначе тест
   валидации нечего проверять.
