# Формулы юнит-экономики

> Реализация: `core/unit-economics.js` (чистый JS, без зависимостей).
> Тесты: `core/core.test.js` — 80 проверок, из них **960 комбинаций round-trip**.
>
> **Round-trip** — главное свойство модели: прямой расчёт (наценка → цена) и
> обратный (цена → наценка) должны быть взаимно обратными. Это подтверждено
> перебором, а не одним примером: 4 значения комиссии × 4 значения ДРР ×
> 3 ленд-коста × 2 логистики × 2 эквайринга × 5 целевых наценок = 960 комбинаций,
> максимальное расхождение < 1e-9.

---

## 1. Обозначения

| Символ | Смысл | Единицы | Откуда |
|---|---|---|---|
| `СС` | Себестоимость за единицу 1С | ₽ | «Номенклатура» F |
| `К` | Кратность | — | «Номенклатура» G |
| `У` | Упаковка | ₽ | «Номенклатура» H |
| `Т` | Транспорт до склада | ₽ | «Номенклатура» I |
| `ЛК` | **Ленд-кост** — полная себестоимость на складе | ₽ | расчёт |
| `c` | Комиссия Ozon | **доля** | «Факт Ozon» W/X |
| `d` | ДРР — доля рекламных расходов | **доля** | «Параметры» B4 |
| `L` | Логистика Ozon | ₽ | «Факт Ozon» I..P |
| `E` | Эквайринг | ₽ | «Факт Ozon» Q |
| `m` | Наценка | **доля** | расчёт |
| `P` | Цена покупателя | ₽ | расчёт / «Факт Ozon» B |

⚠ **Единицы — главное место ошибок.** Комиссия, ДРР и наценка — **доли**
(`0.483`, не `48.3`). Цены, логистика, эквайринг, ленд-кост — **рубли**.
`core/unit-economics.js` принимает и то, и другое через `num()`, который понимает
строки вида `"1 343,66"` — но на выходе всегда доля.

## 2. Ленд-кост

```
ЛК = СС × К + У + Т
```

Кратность нужна, потому что себестоимость в 1С часто заведена за упаковку
(за 10 м.п. кромки), а продаётся товар поштучно.

**Проверенный образец:** СС = 1343,66; К = 0,2; У = 42,89; Т = 0 → **ЛК = 311,61 ₽**

**Правило качества данных:** если нет `СС` или нет `К` — функция возвращает `null`,
и товар **не участвует в расчёте**. Молча считать по нулям нельзя: получится
бесконечная наценка. В модели таких товаров было **111** (109 без себестоимости,
1 без сопоставления с 1С, 2 без кратности) — все помечены, в расчёт не берутся.

⚠ **Упаковка не задана у 1031 товара из 1265.** Это не ошибка, а состояние данных.
Сейчас пустая упаковка считается нулём, из-за чего ленд-кост занижен, а наценка
завышена. В SaaS это должно быть явным флагом «упаковка не задана», а не молчаливым нулём.

## 3. Логистика

Ozon отдаёт **вилку** тарифа (мин/макс), потому что итог зависит от габаритов
и направления. В исходном файле V3 взята середина вилки.

### FBO
```
L_FBO = СРЗНАЧ(магистраль мин; магистраль макс) + Доставка до выдачи
```
**Проверено:** СРЗНАЧ(75; 254) + 25 = 164,5 + 25 = **189,50 ₽**

### FBS
```
L_FBS = СРЗНАЧ(первая миля мин; макс) + СРЗНАЧ(магистраль мин; макс) + Доставка до выдачи
```
**Проверено:** СРЗНАЧ(0; 10) + 164,5 + 25 = 5 + 189,5 = **194,50 ₽**

FBS дороже FBO ровно на первую милю. Нулевая первая миля (`0/0`) делает FBS = FBO.

**Выбор схемы — автоматически**, по остатку на складе Ozon («Номенклатура» L,
«Параметры» B13 = «Авто»). Склад — только МСК.

## 4. Обратный расчёт: наценка по известной цене

```
              P × (1 − c) × (1 − d) − L − E
    m  =  ─────────────────────────────────  −  1
                        ЛК
```

**Смысл по шагам:**
1. `P × (1 − c)` — что осталось после комиссии Ozon;
2. `× (1 − d)` — что осталось после расходов на рекламу;
3. `− L` — минус логистика;
4. `− E` — минус эквайринг;
5. `/ ЛК − 1` — делим на себестоимость и получаем наценку.

**Защиты в реализации:**
- `ЛК ≤ 0` → `null` (иначе `Infinity`);
- `c ≥ 1` → `null` (комиссия 100%+ — бессмыслица, а не ноль);
- пустые `d`, `L`, `E` трактуются как `0` — они legitimately могут отсутствовать;
- пустые `P`, `c`, `ЛК` → `null`, потому что без них расчёт невозможен в принципе.

---

## 5. Прямой расчёт: цена из целевой наценки

Алгебраическое обращение формулы 4:

```
           ЛК × (1 + m) + E + L
    P  =  ───────────────────────
              (1 − c) × (1 − d)
```

Знаменатель `(1 − c) × (1 − d)` выделен в отдельную функцию **`headroom()`** —
«запас цены». Это доля цены, которая доживает до продавца после Ozon и рекламы.

---

## 6. Ограничение для акций

```
    W = цена при МИНИМАЛЬНОЙ наценке
```
Та же формула 5, но с `m = minMarkup` («Параметры» B9, по умолчанию 0,2).

**Смысл:** это пол, ниже которого товар убыточен относительно порога. Он же —
ориентир для `min_price` в Ozon и для того, в какие акции можно заходить.

**Связь с акциями площадки:** Ozon в ответе `/v1/actions/products` отдаёт
собственное поле «максимально допустимая цена акции». Наше `W` и их ограничение
— **две разные границы**, и цена акции должна удовлетворять обеим:
```
    W_наше  ≤  цена акции  ≤  max_допустимая_Ozon
```
Если интервал пуст — в акцию заходить нельзя, и это надо показывать явно.

## 7. Цена безубыточности

```
    P(m = 0) = (ЛК + E + L) / ((1 − c) × (1 − d))
```

## 8. Проверенный образец

«Кромка-Дуб-44мм-5м.п.» (`product_id` 476340284, `sku` 907795882):

| Показатель | Значение |
|---|---|
| Ленд-кост | **311,61 ₽** |
| Цена `S` (с акцией) | 1757 ₽ |
| `min_price` из Ozon | 1615 ₽ |
| Логистика FBO | 189,50 ₽ |
| Логистика FBS | 194,50 ₽ |
| Эквайринг | 10,73 ₽ |
| Комиссия списочная | 49,5% |
| **Наценка по `S`** | **≈ 81,3%** |
| **Наценка по `min_price`** | **≈ 61,3%** |
| **Цена при целевой наценке 30%** | **≈ 1393 ₽** |
| **Цена безубыточности** | **≈ 1180 ₽** |

### ⚠ Важная оговорка про точность этих чисел

Значения выше согласуются с внутренними предположениями прежнего файла V3, но
**не подтверждают семантику полей API**. Пара `c = 48,3%, d = 15%` — значения
старой модели, а не доказательство фактически удержанной комиссии или скидки.

Сырой аудит 18 строк API (12.10.2026) установил, что
`standard_fee / (seller_price_per_instance × quantity)` совпадает с
`commission_ratio`; проценты выше 100% возникали от деления на `amount`, другую
ценовую базу. Аудит не калибрует B14: его значение оставлено без изменений.
См. `docs/API-MAP.md`, раздел 6.

## 9. Второй проверенный образец — негативный

«Кромка-Бук»: **ЛК = 87,34 ₽**, цена `S` = **680 ₽**, а ограничение для акций
`W` = **700 ₽**.

**`S < W`** — текущая цена уже **ниже** минимально допустимой. Товар торгуется
с наценкой ниже порога. Это не ошибка расчёта, а реальная проблема в прайсе,
и модель должна её подсвечивать (в `core/unit-economics.js` — массив `warnings`).

Подобные случаи — главный аргумент в пользу автоматизации: вручную такие
расхождения в 1265 строках не находятся.

## 10. Что ещё считается

### ДРР
```
    ДРР = Расход на рекламу / ВСЯ выручка товара
```
**Вся** — и органическая, и рекламная. Это прямое требование пользователя,
а не «расход / продажи в продвижении». Числитель — Performance API
(единственный источник, см. `docs/API-MAP.md`), знаменатель — `revenue`
из `/v1/analytics/data` по `sku`.

Если выручки по SKU нет (товар не продавался в периоде), ДРР берётся из
параметра B4 — общая ставка по умолчанию, с фиксацией источника в C4.

### % выкупа (Premium Plus)
```
    % выкупа = delivered_units / ordered_units
```
При `ordered_units = 0` **не пишется ничего**, а не ноль.

### Фактическая комиссия
```
    база комиссии    = seller_price_per_instance × delivery_commission.quantity
    ставка категории = commission_ratio                           (нормализовано к %)
    комиссия факт    = standard_fee / база комиссии × 100
    разница, п.п.    = ставка категории − комиссия факт
    ожидаемый total  = amount − standard_fee + bonus + bank_coinvestment
                       + stars + pick_up_point_coinvestment + compensation
```
Взвешивание — **по базе продавца**, не по `delivery_commission.amount` и не
среднее по артикулам. Аудит 18 реальных строк подтвердил базу; он не калибрует
B14. Подробности — `core/commission.js` и `docs/API-MAP.md` §6.

### НДС
Ставка — переменная, **только 22%**, льготных ставок нет. ОСНО, налог на прибыль 25%.
`vat` из API приходит долей (`"0.22"`) и приводится к процентам.

## 11. Что НЕ реализовано (осознанные пробелы)

| Пробел | Статус | Где |
|---|---|---|
| Каскад целевой наценки общая → категория → SKU | не начато | трекер, этап Э3 |
| Правила округления цены | делегировано | трекер, Э3.5; шаг есть в B11, применение нет |
| Ставка комиссии по каждому SKU (вместо общей скидки) | не начато | трекер, задача 2.10 |
| Возвраты в деньгах | частично | есть тариф возврата FBO/FBS, фактические возвраты — средним по SKU |
| Налог на прибыль в наценке | параметр есть | B7 = 0.25, в формулы не входит |

**Про налог на прибыль важно:** сейчас наценка считается **до** налога. Параметр
B7 заведён, но в формулах 4–5 не участвует. Если считать «чистую» наценку,
знаменатель изменится. Это не баг, а незакрытое решение — зафиксировано здесь,
чтобы не принять текущее поведение за окончательное.
