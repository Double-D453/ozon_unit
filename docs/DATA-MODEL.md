# Модель данных: листы Google Sheets → схема БД

> Таблица — это прототип хранилища. Здесь зафиксирована раскладка каждого листа
> на **октябрь 2026 (каркас v0.7)** и то, во что она превращается в SaaS.
> Индексы колонок менять нельзя молча: часть функций читает данные по позициям
> (например, `salesRevenueMap_` читает колонки B, D, H листа «Продажи»).

Все листы создаются и пересоздаются функцией `ensureSheets()` (`04_Diagnostics.gs`).
Шапка перезаписывается каждый раз — так миграция ширины листа происходит сама:
в v0.7 «Продажи» расширились с 9 до 13 колонок, и старый лист перестроился
без ручного вмешательства.

**Проверка раскладки:** `sheetLayoutDiffers_()` сравнивает фактическую ширину
и шапку с ожидаемой; `validateWorkbook()` печатает расхождения по всем листам.

## 1. «Факт Ozon» — 24 колонки (A..X)

Срез тарифов и цен по каждому артикулу. Источник: `/v5/product/info/prices`
и `/v4/product/info/stocks`. Перезаписывается целиком при каждом синке.

| Кол. | Поле | Тип | Источник |
|---|---|---|---|
| A | Offer id | text | `items[].offer_id` |
| B | Цена с акцией, ₽ | number | `price.price` |
| C | Цена без акции, ₽ | number | `price.old_price` |
| D | Зачёркнутая цена, ₽ | number | `price.marketing_seller_price` |
| E | min_price, ₽ | number | `price.min_price` |
| F | НДС, % | number | `price.vat` — **доля → проценты** |
| G | Комиссия FBO (списочная), % | number | `commissions.sales_percent_fbo` |
| H | Комиссия FBS (списочная), % | number | `commissions.sales_percent_fbs` |
| I | Логистика FBO мин, ₽ | number | `fbo_direct_flow_trans_min_amount` |
| J | Логистика FBO макс, ₽ | number | `fbo_direct_flow_trans_max_amount` |
| K | Доставка до выдачи FBO, ₽ | number | `fbo_deliv_to_customer_amount` |
| L | Первая миля FBS мин, ₽ | number | `fbs_first_mile_min_amount` |
| M | Первая миля FBS макс, ₽ | number | `fbs_first_mile_max_amount` |
| N | Логистика FBS мин, ₽ | number | `fbs_direct_flow_trans_min_amount` |
| O | Логистика FBS макс, ₽ | number | `fbs_direct_flow_trans_max_amount` |
| P | Доставка до выдачи FBS, ₽ | number | `fbs_deliv_to_customer_amount` |
| Q | Эквайринг, ₽ | number | **`items[].acquiring` — в КОРНЕ элемента** |
| R | Остаток FBO, шт | number | `/v4/product/info/stocks` |
| S | Остаток FBS, шт | number | `/v4/product/info/stocks` |
| T | Дата среза | date | момент синка |
| U | Возвраты FBO, ₽ | number | `fbo_return_flow_amount` |
| V | Возвраты FBS, ₽ | number | `fbs_return_flow_amount` |
| **W** | **Комиссия к расчёту FBO, %** | number | **G − скидка из «Параметры» B14** |
| **X** | **Комиссия к расчёту FBS, %** | number | **H − скидка из «Параметры» B14** |

**W и X — единственные расчётные колонки листа.** Всё остальное — сырой факт из API.
Разделение намеренное: сырые данные можно перепроверить, расчётные — пересчитать
одной кнопкой, не трогая источник.

⚠ В прогоне v0.5 эквайринг из API заполнился для 1263 артикулов, для 2 пришлось
ставить оценку — потому что `acquiring` лежит в корне, а не в `price`.

## 2. «Номенклатура» — 17 колонок (A..Q)

Справочник товара. **Единственный лист, где живут данные из 1С**, — всё остальное
приходит из Ozon. Отсюда же берётся себестоимость.

| Кол. | Поле | Источник |
|---|---|---|
| A | Offer id | Ozon / 1С |
| B | SKU | Ozon (`sku`) — **колонка с формулами в I, проверять `getFormulas()` по B** |
| C | Наименование | 1С / Ozon |
| D | Код 1С | 1С |
| E | Номенклатура 1С | 1С |
| F | Себестоимость за ед., ₽ | 1С |
| G | Кратность | 1С |
| H | Упаковка, ₽ | 1С |
| **I** | **Ленд-кост, ₽** | **ФОРМУЛА — не перезаписывать** |
| J | Вес, кг | 1С / Ozon |
| K | Объём, л | 1С / Ozon |
| L | Остаток Ozon, шт | Ozon |
| M | Остаток свои, шт | 1С |
| N | Схема (FBO/FBS) | расчёт: авто по остатку на складе Ozon |
| O | Статус | Ozon |
| P | Категория | Ozon |
| **Q** | **Синк с Ozon** | **флаги качества данных** |

**Ленд-кост считается формулой в самом листе**, а не скриптом:
`I = F × G + H + Транспорт`. `copyLandCostFormula_()` распространяет формулу на
новые строки. В SaaS это уезжает в `core/unit-economics.js → landCost()` — уже
реализовано и протестировано.

### Флаги в колонке Q (правила качества данных)

| Флаг | Значение | Что делает система |
|---|---|---|
| `новый из Ozon — нет данных 1С` | карточка появилась в магазине, сопоставления с 1С нет | **добавляет строку и помечает**, в расчёт не берёт |
| `нет в магазине Ozon` | есть в 1С, нет в Ozon | помечает |
| `нет карточки/цен в Ozon` | карточка есть, цен API не отдал | помечает |
| `нет себестоимости (1С)` | нельзя посчитать ленд-кост | помечает |
| `дубль Offer id (N строк)` | один и тот же артикул несколько раз | помечает все дубли |

**Ключевое требование пользователя:** номенклатура обновляется из Ozon полностью
автоматически, **но с валидацией** — новые карточки без сопоставления с 1С
помечаются, а не считаются молча. Это реализовано как `addMissingSkus()` +
`addProblems_()` + колонка Q.

Дубли Offer id детектируются в `syncFact` (v0.7): пишутся в лог как `WARN`,
в лист «Проблемы данных», и возвращаются в результате синка полями
`uniqueOffers` и `duplicates` — чтобы их можно было увидеть, не открывая таблицу.

## 3. «Продажи» — 13 колонок (A..M)

Источник: `/v1/analytics/data`. С v0.7 добавлены Premium-метрики.

| Кол. | Поле | Метрика | Доступность |
|---|---|---|---|
| A | Offer id | — | всем |
| B | SKU | `dimension: sku` | всем |
| C | Название | — | всем |
| D | Выручка, ₽ | `revenue` | всем |
| E | Заказано, шт | `ordered_units` | всем |
| F | Расход на рекламу, ₽ | — | **из Performance API** |
| G | ДРР, % | расчёт: F / D | расчётное |
| H | Период | — | всем |
| I | Дата среза | — | всем |
| **J** | **Доставлено, шт** | `delivered_units` | **Premium Plus** |
| **K** | **Возвраты, шт** | `returns` | **Premium Plus** |
| **L** | **Отмены, шт** | `cancellations` | **Premium Plus** |
| **M** | **% выкупа** | расчёт: J / E | **Premium Plus** |

**Итоги — в `O1:P8`** (переехали с прежнего места при расширении листа).

⚠ **`salesRevenueMap_()` читает колонки B, D, H по индексам.** Индексы не
менялись при расширении листа — новые метрики добавлены справа. Это правило:
**новые поля добавлять в конец, не вставлять в середину**, иначе ломаются все
читатели по позициям.

⚠ **Защита от деления на ноль:** при `delivered_units = 0` пишется `WARN`,
и **% выкупа не пишется вообще**, а не как 0. Ноль и «нет данных» — разные вещи,
и в модели они должны выглядеть по-разному.

В прогоне на синтетике: 13 колонок, % выкупа 92,96% — тест `comm7.js`.

## 4. «Реклама ДРР» — 14 колонок (A..N)

Источник: Performance API. Ключ накопления — **B (SKU)**; если SKU нет,
строка пишется как `КАМПАНИЯ <id>`, чтобы расход не терялся.

**Итоги — в `P1:Q10`.**

Данные сюда приходят волнами и **накапливаются**, а не перезаписываются:
состояние обработанных кампаний живёт в `Script Properties` (`DRR_DONE_0…`,
чанки по 600 id из-за лимита значения 9 КБ). Прогон повторяют до сообщения
«осталось 0 кампаний».

## 5. «Комиссия факт» — 13 колонок (A..M)

Источник: отчёт о реализации (`/v1/finance/realization/by-day` → `/v2/finance/realization`
→ отправления, каскад). Создаётся `diagCommission()`.

| Кол. | Поле |
|---|---|
| A | Offer id |
| B | SKU |
| C | Наименование |
| D | Реализовано, ₽ (`delivery_commission.amount`) |
| E | База комиссии, ₽ (`seller_price_per_instance × quantity`) |
| F | Комиссия удержана, ₽ (`standard_fee`) |
| G | К начислению, ₽ (`total`) |
| H | Продано, шт (`quantity`) |
| I | Ставка по категории, % (`commission_ratio`, нормализовано) |
| J | Комиссия факт, % (`F / E × 100`) |
| K | Разница, п.п. (`I − J`) |
| L | Источник (`по дням` / `за месяц` / `отправления FBO/FBS`) |
| M | Период |

**Итоги — в `N1:O12`**: источник и период; число артикулов; реализация; база
продавца; удержанная комиссия; `total`; корректировки; ставка категории;
фактическая ставка; разница; медиана и разброс.

Аудит 18 строк API подтвердил, что `standard_fee` соответствует
`commission_ratio` от `seller_price_per_instance × quantity`. `amount` — другая
ценовая база, его нельзя использовать в знаменателе. Контроль начисления считает:
`total = amount − standard_fee + bonus + bank_coinvestment + stars +
 pick_up_point_coinvestment + compensation`.

B14 остаётся без изменений по этому аудиту. В дальнейшем диагностика обновляет
его только при ≥10 SKU, заполненной базе, положительной разнице ставок и
прошедшей сверке `total` с корректировками; иначе значение не меняется.

В v0.6 этот лист оставался **пустым** — причина в неверной форме запроса к FBO
(см. `docs/API-MAP.md`, раздел 0 и 4).

## 6. «Проблемы данных» — 4 колонки

Журнал качества данных. `addProblems_()` **дедуплицирует по паре A+C**,
поэтому повторные синки не размножают строки.

| Кол. | Поле |
|---|---|
| A | Offer id |
| B | Наименование |
| C | Что не хватает |
| D | Что делать |

**Уведомления о новых карточках пользователю НЕ нужны** (ответ на вопрос №20) —
достаточно пометки в колонке Q «Номенклатуры» и записи в этом листе.

## 7. «Акции» — 15 колонок (11 из API + 4 расчётные)

Источник: `/v1/actions` + `/v1/actions/products` (колонки `A..K`) и расчёт `calculateUnitEconomics()` (колонки `L..O`).

`Акция(ID)` | `Название` | `Offer id` | `Product id` | `Цена до акции` |
`Цена акции` | `Макс. допустимая` | `Мин. кол-во` | `В акции, шт` |
`Способ` | `Дата среза` | `Наш мин. пол, ₽` | `Запас к лимиту Ozon, ₽` |
`Наценка по цене акции, %` | `Статус ограничения`

«Макс. допустимая» (`G`) — ограничение площадки Ozon; `Наш мин. пол, ₽` (`L`) —
округлённый вверх минимальный пол по SKU. Условие прохождения ограничения акции:
**наш минимальный пол должен быть не выше лимита Ozon** (`L ≤ G`). При `L > G`
строка получает статус `КОНФЛИКТ: наш пол выше лимита Ozon`. Никаких изменений
цены на Ozon не отправляется (Э5 вне рамок).

## 8. «Параметры» — управляющие константы

Создаётся `ensureParams_()`. **Поиск по тексту в колонке A** (регулярное
выражение), а не по номеру строки — иначе вставка строки ломает всё.

| Строка | Параметр | Значение по умолчанию | Формат |
|---|---|---|---|
| B4 | ДРР | `0.15` | 0.0% |
| B5 | Эквайринг | `0.015` | доля |
| B6 | НДС | `0.22` | доля |
| B7 | Налог на прибыль | `0.25` | доля |
| B8 | % выкупа | `1` | доля |
| B9 | Минимальная наценка | `0.2` | доля |
| B10 | Целевая наценка | `0.3` | доля |
| B11 | Шаг округления цены | `1` | ₽ |
| B12 | Склад | `МСК` | text |
| B13 | Схема | `Авто` | text |
| **B14** | **Скидка к комиссии Ozon (отсрочка выплаты), п.п.** | **`1.5`** | п.п. |

**Про B14 критично:** значение `1.5` — существующая настройка по умолчанию,
не результат измерения. Аудит 18 строк показал совпадение ставки комиссии с
`commission_ratio`; B14 этим аудитом не калибровался и остаётся без изменений.
В дальнейшем диагностический отчёт может обновить B14 только при ≥10 SKU,
положительной разнице ставок и прошедшей сверке `total` с корректировками.
Колонка C4 фиксирует источник ДРР (`writeDrrParam_`).

Поиск B14 — по `/скидка к комиссии/i`.

## 9. «Настройки расчёта» и «Расчёт» (Э2/Э3)

Реализовано в `appsscript/05_Calculation.gs` и `core/unit-economics.js`:

1. **Лист «Настройки расчёта» (`5 колонок`)**:
   `Уровень (SKU / Категория)` | `Ключ (Offer id / SKU / Категория)` | `Целевая наценка, %` | `Мин. наценка, %` | `Комментарий`
   - Реализует каскад: **SKU → категория (`Номенклатура!P`) → общая (`Параметры!B10/B9`)**.
   - Пустая колонка `Номенклатура!P` дозаполняется значением `category_id` из Ozon при `syncFact()` без перезаписи существующих значений.

2. **Лист «Расчёт» (`40 колонок`)**:
   - Содержит по каждому SKU статьи затрат (`СС`, `Кратность`, `Упаковка`, `Ленд-кост`, прямая логистика, тариф возврата, `% выкупа` из `Продажи!M` или `Параметры!B8`, ожидаемый возврат на выкупленную единицу `тариф возврата × (1 − выкуп) / выкуп`, эквайринг, ставка комиссии с приоритетом `Комиссия факт!J → Факт Ozon!W/X`, ДРР и запас цены `headroom`).
   - Считает фактические наценки по 4 ценам (`Цена с акцией`, `Цена без акции`, `Зачёркнутая цена`, `min_price Ozon`).
   - Считает безубыточную цену, ограничение для акций (наш пол) и целевую цену по проверенной формуле **до налогов** с округлением **вверх** по шагу `Параметры!B11`.
   - При выкупе `0%` принимает валидные `0%`, но **блокирует цену** с предупреждением о неограниченном возврате.
   - Показывает НДС и налог на прибыль отдельно (неподтверждённый входящий НДС из цены не вычитается).

## 10. Во что это превращается в SaaS

| Лист | Сущность в БД | Комментарий |
|---|---|---|
| «Номенклатура» | `product` + `product_cost` (история себестоимости) | себестоимость меняется — нужна версионность |
| «Факт Ozon» | `ozon_price_snapshot` | **срез во времени, не текущее состояние** |
| «Продажи» | `sales_period` (tenant, sku, period, метрики) | период — часть ключа |
| «Реклама ДРР» | `ad_spend` + `campaign` | накопление → идемпотентный upsert |
| «Комиссия факт» | `commission_snapshot` | источник и период обязательны |
| «Проблемы данных» | `data_issue` (tenant, sku, kind, resolved_at) | из листа — в очередь задач |
| «Акции» | `promotion` + `promotion_product` | |
| «Параметры» | `tenant_setting` (ключ/значение) | **каскад общая→категория→SKU** = отдельная таблица с `scope` |

**Три вещи, которые в таблице были бесплатными, а в SaaS надо проектировать:**

1. **Мультитенантность.** Каждый лист сейчас — один магазин. В SaaS у каждой
   строки должен быть `tenant_id`, и все запросы — через него. Это нельзя
   добавить потом, только сразу.
2. **Историчность.** «Факт Ozon» перезаписывается целиком, история тарифов
   теряется. Для расчёта наценки «как было в сентябре» нужен снапшот с датой.
3. **Идемпотентность синков.** В таблице перезапись скрывает повторные запуски.
   В SaaS воркер может упасть на середине — нужен upsert по естественному ключу
   и отметка выполненной работы, аналог `DRR_DONE_*`.

Подробный план — `docs/ROADMAP-SAAS.md`.
