## 1. Что это за проект (одним абзацем)

Продавец на Ozon (стройматериалы, кромка ПВХ, ~1400 SKU, склад МСК, ОСНО + НДС 22%)
ведёт расчёт юнит-экономики в Google Таблицах. Исходный файл — «Калькулятор Озон V 3»:
65 колонок шаблона Ozon (A:BM) плюс формулы (BM:CN), заполняется **вручную**.
Задача — автоматизировать: тянуть факт из API Ozon, считать наценку по каждому SKU,
обратным расчётом получать целевую цену и «ограничение для акций».
Построен каркас на Apps Script v0.8 (5 файлов, 3 123 строки, 97 функций) и
таск-трекер в Google Sheets, который пользователь правит сам.
**С 09.10.2026 цель изменилась: переделать MVP в SaaS.**

## 5. Как запускать тесты

```bash
# каркас Apps Script (9 тестов)
cd tests && ./prepare.sh                     # скопировать .gs → .js
TESTFILE=schema.js node all.js               # любой из 9: fact fact6 test_drr guard smoke schema negative comm7 log_sink

# доменное ядро (80 проверок, без подготовки)
node core/core.test.js
```

Тестовый стенд — **Node-only, CI-ready**, ни одного обращения к сети или к Google.
`tests/env.js` содержит мок Apps Script. **Мок валидирует не только число строк,
но и ширину каждой строки в `setValues`** — это поймало реальную ошибку
(`CFG.DRR_COLS` был 13 при 14 колонках: в Apps Script бросило бы исключение,
а прежний мок молча пропустил). **Эту проверку не убирать.**

## 6. Критические факты, которые нельзя вывести заново

Полностью — в `docs/API-MAP.md`. Здесь только то, что ломает работу молча:

1. **`adv_sum_all` не существует.** 0 вхождений в официальной схеме. Расходы на
   рекламу — **только Performance API**. Раньше в коде было написано, что метрика
   «доступна с Premium и скрипт пробует её и откатывается» — запрос был обречён.
2. **FBO и FBS — разные формы запроса.** У FBO `cursor`/`sort_dir`/`limit≤100`
   и ответ **без `result`**; у FBS `dir`/`offset` и ответ в `result.postings`.
   Лишнее поле = HTTP 400. Неправильный путь чтения = молча пустой массив.
3. **`acquiring` — в КОРНЕ элемента** `/v5/product/info/prices`, не внутри `price`.
4. **`vat` приходит долей** (`"0.22"`), таблица ждёт проценты.
5. **`/v1/actions/products` — пагинация через `last_id`**, поля `offset` там нет.
6. **`date_to` в будущем = 400** в `/v1/analytics/data`.
7. **`/v3/finance/transaction/list` отключён 08.09.2026.** Любой код из статей
   в интернете обращается к нему. Замена — `/v1/finance/accrual/*`, но там
   **сборы**, а не выручка за продажу.
8. **`performance.ozon.ru` мёртв с 15.01.2025** (307). `UrlFetchApp` не повторяет
   POST при 3xx → нужен `fetchWithRedirects_`.
9. **Комиссия из отчёта о реализации:** `standard_fee / (seller_price_per_instance × quantity)`.
   Аудит 18 строк подтвердил, что `amount` — другая база и что фактическая ставка
   совпадает с `commission_ratio`. Не калибровать B14 этим аудитом.
10. **`commission_amount` неоднозначен** (за единицу или за позицию) → решено
    самокалибровкой по `commission_percent`, а не догадкой.

## 7. Чего НЕ делать

Полный реестр — `docs/DECISIONS.md` §G. Критичное:

- ❌ **Не предлагать уведомления о новых карточках** (почта, алерты). Пользователь
  отказался явно (вопрос №20). Достаточно пометки в колонке Q и листа «Проблемы данных».
- ❌ **Не хранить ключи в таблице.** Только `Script Properties` (вопрос №14).
  Ключи уже хранились открыто и были перевыпущены.
- ❌ **Не класть GitHub-токен в песочницу.** Отклонено по тому же правилу.
- ❌ **Не вызывать `deleteAllProperties()`** — сотрёт API-ключи вместе с состоянием.
- ❌ **Не перезаливать файл рабочей модели на Drive** (раздел 3).
- ❌ **Не вставлять новые колонки в середину листов** — часть кода читает по индексам.
  Только добавлять в конец.
- ❌ **Не искать витринную цену покупателя через API** — `marketing_price` отключён
  12.11.2025, пользователь пробовал.
- ❌ **Не выдавать B14 = 1,5 за измеренную скидку.** Это дефолт.
- ❌ **Не предлагать `adv_sum_all`** как источник расходов на рекламу.

## 8. Как общаться с пользователем

- **Язык — русский.** Всегда.
- **Поступательно, поэтапно.** Не выкатывать большие изменения одним куском.
- **Пользователь правит трекер сам** — трекер источник правды по задачам,
  не переписывать его «под себя».
- **Пользователь требует объяснять**, значение получено автоматически или
  поставлено вручную (вопрос №19). Это касается B14, ДРР, оценок по умолчанию.
- **Не додумывать вводные.** Если данных нет — спрашивать через `ask_user`,
  а не предполагать. Вопросы, на которые уже получены ответы, — в `docs/DECISIONS.md`.
- Пользователь **не технарь в части API**, но точно знает свой бизнес:
  себестоимость, кратность, отсрочку выплаты, категории. Его поправки по сути
  бизнеса авторитетнее любой документации.
